Part I — Current work

0. Revised scope (2026-11-06)

The primary deliverable is now the prompt-only path: a modified harness system prompt plus the fork/join runtime. The initial target is transparent best-of-N — the user asks once, the harness exposes fork/message/end, the runtime isolates execution, the swarm selects and integrates, and the user sees one result. No fine-tuning is required for this first stage.

This replaces the training-first framing. The staged training experiment in §10 is retained as a deferred track, not a prerequisite. A model trained to use the interface is a later optimization: it moves the prompt's instructions into weights, frees context, and may improve reliability, but it is not part of the immediate work.

Why this is the right first target:
- It tests the interface before spending training compute and produces evidence for the training design. Failure to elicit useful organization through prompting does not gate training.
- It is the product surface. The harness system prompt is what users actually run; the runtime is the substrate underneath.
- It is cheap. Inference and runtime only; no data generation, fine-tuning, or checkpoint export.
- It produces the traces and winning prompts that a later training stage would distill.

What it can and cannot claim:
- It can improve the cost-performance frontier through better delivered correctness, lower total dollar cost, or lower task latency, while keeping branch management transparent to the user.
- It cannot exceed the model's ability to judge when to fork and which result to keep. Prompt engineering may plateau; that is a finding, not a failure.
- Selection needs evidence; tests and validators are the strongest source where they exist, and gathering evidence is part of the swarm's job.
- It must disclose cost to the operator even while hiding branch management from the user.

Terminology: elastic harness. One name for the capability. An elastic harness is an agent harness that allocates inference-time compute dynamically: it branches the agent's execution — session, tools, environment, and model calls — when an alternative is worth exploring, joins results when evidence arrives, and stops when the budget or the evidence says to. The user sees one request and one result; the harness absorbs the branching. This is the name. "Dynamic branching" describes the mechanism, "transparent best-of-N" describes the benefit for users who know the baseline, and "adaptive inference-time scaling" is the academic umbrella. The distinction from session branching (conversation only) and server-side search (reasoning only) is that the elastic harness branches the execution across both sides. Best-of-N fixes five things — the fork point (at the start), N (constant), the branches (homogeneous samples), their interaction (none), and the decision point (after all N finish); the elastic harness relaxes all five. Prior use of the exact phrase is a small unrelated state-machine harness project; Harness.io is a different domain.

0.1 Premise: copies are the native affordance

Humans have a single continuing existence and cannot trivially copy themselves into simultaneous continuations. That pattern casts a shadow over how we design agents, without imposing a hard constraint on model reasoning: models can revisit, connect, and reorganize information in ways that need not resemble a linear human explanation. A digital agent can additionally copy its working state and pursue several continuations at once. The tree of existences is the parallel form of scaling.

Copying lowers the burden of asking for help. Invoking a specialized subagent or predefined workflow ordinarily asks the agent to recognize both that it needs help and what kind of help to request. A fork can require only the judgment that another continuation could be useful. The copy inherits the situation and can discover what work is needed. A detailed task decomposition or specialist brief is optional. This also preserves information whose importance the parent has not yet recognized and therefore might omit from a delegation brief.

The central contribution sought is a loom that includes the state of the computer itself: the session and the executable workspace branch together. A copy can act on the files, artifacts, and tool results accumulated so far without reconstructing the situation from a description. That continuity is the basis for transparency to the agent and for making organization an ordinary, trainable part of execution. The first version preserves session and filesystem state; VM memory and live-process preservation are deferred. The snapshot mechanism must let the source continue operating and changing while the copy has a stable starting state.

Copies provide a way to add inference work using the same model and, at a given serving point, the same token prices. A further economic hypothesis is that learned parallel organization can let inference run at a cheaper dollars-per-token operating point while maintaining delivered correctness and end-to-end task latency. Useful concurrency may make efficient batching compatible with the task's latency target, even when individual requests are slower. Selection, communication, and integration are part of that task latency and cost. They do not have to be cheap; they have to be visible, priced, and trainable. This depends on useful parallel work and available serving capacity; copies that merely queue do not provide the benefit.

The project takes the bitter lesson seriously: expose a generic fork/join primitive and a budget, and learn the organization policy from outcomes. When to fork, where, how wide, how much context to inherit, what each branch should do, what and when to communicate, what evidence to use, which results to incorporate, and when to stop are the learned object. The swarm also owns selection and final delivery. The runtime provides the mechanisms and enforces resource limits; the primitive is the scalable action space.

Best-of-N supplies the motivation for expecting a small initial learning signal: where additional attempts help, there should be useful organization to capture. Matching small-N best-of-N is an engineering target, and the empirical question is how far learning can extend that benefit. Begin with ordinary tasks that benefit from multiple attempts; specially constructed decomposition tasks are not a prerequisite. The main result is the cost-performance Pareto frontier, including dollar cost and task latency, with outcome-labeled traces available for further learning.

1. Objective and proposed contribution

Test whether a coding model can learn to organize its own computation through recursive forks of the session and executable workspace. One external request should produce one coherent, validated result. Internally, the swarm determines how many branches to create, where to create them, what context to inherit, what information to exchange, which results to incorporate, and when sessions should stop. The number of branches, N, emerges from execution within a resource budget. The proposed contribution centers on incorporating computer state into the loom so that these choices can be transparent, executable, and trainable.

The first engineering target is to obtain the benefit of multiple attempts while spending less than a naive fixed-N implementation. Savings could come from sharing work before forks, exploring only meaningful alternatives, reusing discoveries, and stopping unproductive work. Selection, integration, and environment cleanup belong inside the system. Deployment should fit existing tool-enabled workflows without requiring an additional external judge or a human to manage branches.

2. The product gap: best-of-N is not a primitive

Today, best-of-N with a day-to-day agent requires explicit orchestration. The user or harness must ask for multiple attempts, define N, isolate the environments, collect the results, and select. The available forms are all manual:
- Prompt the model to try several approaches. It serializes them, explores superficially, and has no isolated environments.
- Spawn N subagents or parallel sessions. The user defines N and the task split; the workspace is shared or manually worktreed; selection is manual.
- Use an API n parameter. That samples tokens, not tool-using sessions, and provides no environment isolation.
- Build a fixed-N pipeline. N and cost are fixed, with no adaptivity and no reuse across attempts.

What is missing is not the algorithm; best-of-N is well understood. What is missing is the packaging: one request in, internal exploration, selection by execution feedback, and one result out, with the user never managing branches. The transparent version requires:
- A cheap environment fork, so an attempt does not replay setup.
- A fork tool the model can see and learn to use, rather than an orchestration the user writes.
- Evidence for selection: tests, validators, or executable checks where available.
- Budget control and a visible cost line, because transparency to the user must not mean invisibility of the bill.
- Cleanup and provenance, so the user gets one workspace and the runtime keeps the loom.

This is the product thesis, and it is distinct from "a smarter model": the same model gets multiple attempts without the user managing them. The swarm decides when to fork, what to communicate, which results to incorporate, and how to deliver the final result; the runtime isolates execution, accounts for resources, and handles cleanup; the user sees one result.

User-visible capability is a property of the system, not the weights. A transparent runtime that explores internally is indistinguishable, at the interface, from a smarter model: same request, same output shape, better answer. That is the intended product claim. The scientific claim is separate: the weights are unchanged, and any gain comes from organization at matched or lower cost. Keep the two claims distinct so neither borrows the other's evidence. The product claim is only honest if the interface really is unchanged and the cost is disclosed to the operator, even when it is hidden from the user.

2.1 Evidence status

No published controlled result shows that these fork tools improve agent benchmark scores. Their evaluations are systems metrics:
- BranchFS: 292-317 microseconds branch creation, 317 microseconds to 2.1 ms commit, 1.66 GB/s FUSE read (7.24 GB/s with passthrough). No task accuracy.
- LayerFS: filesystem benchmarks (1.71x faster than the comparison image on fs-bench, 19.9x smaller than btrfs + zstd on a 157-snapshot history, zero unexpected pjdfstest failures). No agent accuracy.
- simgit: 10 MiB versus 567 MiB per microsoft/vscode worktree; eight worktrees in 6.4-7.0 s versus 14.0-14.2 s. No agent accuracy.
- Waypoint: checkpoint/fork timings. No agent accuracy.
- BranchContext: exploration patterns and filesystem numbers. No agent accuracy.

The accuracy evidence is at the strategy level, not the fork-tool level. EnCompass (NeurIPS 2025) reports an ARC subset rising from 4.3% for a two-step agent to 11.7% with best-of-8 and 16.0% with best-of-36 (GPT-3.5), and a Reflexion agent moving from 35.5% to 36.1% with best-first search at lower cost per task. Best-of-N, self-consistency, Tree of Thoughts, Reflexion, and beam search all have published gains, but they come from sampling and selection, not from forking the workspace.

The fork tool is an efficiency enabler: it can improve accuracy at a fixed budget by making exploration cheaper, and it can improve latency by reusing setup. It is not itself an accuracy method.

3. What a loom means

A branch is a fork of a session and the relevant executable environment. The initial version preserves session and filesystem state, starts a fresh executor, and makes the environment guarantees explicit. VM memory and live-process preservation belong to a later version. A branch normally inherits the session history; a candidate fresh-context mode can omit the parent's reasoning while preserving the task and executable workspace (§5). A detailed child assignment is optional: the child can discover its own useful continuation. Define the snapshot boundary for the chosen backend before selecting models and tasks.

A join incorporates selected artifacts, findings, and context from another branch. Integration happens through agent communication (§6); preserve provenance and validate the resulting artifact. Arbitrary process memories are not assumed to be automatically mergeable.

Every session has identical privileges and capabilities. It may work, fork, message peers, incorporate results, or stop itself. A session does not become a privileged coordinator (the root differs only in delivering the result to the user) and cannot unilaterally kill other sessions. The runtime enforces shared resource limits and handles environment lifecycle cleanup.

4. Stage 0: prompt-learned organization

Stage 0 (primary): prompt-only fork/join. Fix a strong tool-enabled model and the runtime; modify the harness system prompt to expose fork/message/end and a compact loom view; search a population of prompts genetically on development tasks. Fitness is delivered correctness minus a cost penalty, on paired tasks, with repeated seeds. Baselines: single session, fixed-N=5, serial retry at matched budget, and the untrained model without the tools. No training. This stage answers whether the interface is usable and whether transparent best-of-N beats the baselines at matched cost. It is the primary deliverable. Reuse the genetic prompt-search discipline from the project-manager document-generation experiment: population rather than one running best, sparse cumulative evaluation, stored evaluations never repeated, held-out cases, and the search cost counted in the budget.

Before fine-tuning, test whether the fork/join interface is usable by a strong model with a learned prompt. This is cheaper than training and answers a prior question: can the policy be elicited at all?

- Fix the runtime and the model; vary only the system prompt and few-shot examples. Search a population of prompts genetically, with sections for when to fork, how many, what to send, when to join, when to stop, and how to read the loom.
- Fitness: delivered correctness minus a cost penalty, on paired development tasks; multiple seeds; held-out evaluation. Include fixed-N=5 and a matched-budget single stream as baselines.
- Use prompt-only successes and failures to inform the interface and training design. Winning prompts and traces can supply a teacher policy and distillation targets; failure to beat fixed-N through prompting does not gate training.
- Run a capability gradient: strong model prompt-learned, then a mid-size open model (7B-32B, local) prompt-learned, then distill to the 0.5B-3B student. This separates "the interface is learnable" from "a tiny model can execute it."
- Teacher-checkpoint intervention remains a separate Stage B mechanism. It can use the fork primitive to sample K interventions from one checkpoint, execute each in a fork, and select by outcome.

4.1 Loom observation for the fork decision

The deciding session needs a compact observation, not the full loom: branch ids, goals, status, last emission as a short string, per-branch cost in tokens, wall clock and disk, remaining budget, depth, and the marginal cost of one more fork. Without cost the model cannot make a value-of-computation decision; without the summary it cannot see what is already being tried.

The compact view is the default, not the only view. Any branch's full trace is readable on demand (history://<branch> or an equivalent tool), and inspection is a tool call, not an elicitation prompt. That gives the model two learned behaviors: infer the loom from summaries, and ask for a trace when the summaries are insufficient. Inspection is an ordinary tool call in the trace; it needs no special logging. Fewer inspections are rewarded by the cost term, so the model learns when a label is enough.

Use emissions, not transcripts, and keep the compact observation small enough for a 0.5B-3B student. This is the minimal-emission discipline applied to the policy's input.

4.2 The existing session label as a peer-facing summary

The summary already exists. It is the few-word description a session generates for a picker or status bar, derived from its task or current activity. It is not a new artifact and it is not trained today. Putting it in the loom observation changes its role: it becomes the peer's default view of what a branch is doing, so it becomes load-bearing and therefore trainable as a communication channel.

There is no separate summarization objective and no automated sufficiency measure. The label is part of the trace. Traces that deliver a correct result at acceptable cost are selected for training, and the labels in them are reinforced along with the rest of the decisions. Labels that mislead tend to appear in traces that fail, recover, or are filtered out. Selection does the work; no per-label comparison is needed.

- Emit the existing label and cost at every turn or branch boundary, not only when eliciting. That puts the label in the trace consistently and makes it part of the model's normal output.
- Keep inspection available, but do not score the label against it. Inspection is an action in the trace like any other; its use is learned from the same outcome and cost signal.
- Write the label for the peer's decision, not only for the human's picker. "Testing retry backoff" is fine for both; "exploring alternative A because the first failed on the boundary case" is better for the peer and still readable in a picker. The runtime keeps the same field and lets the model choose the content.
- The label is trained by inclusion in successful traces, not by a dedicated loss.

5. MVP: ephemeral CoW filesystem forks, no explicit join

The MVP is one new primitive — a filesystem fork that accompanies the session fork — plus the existing message passing. The snapshot mechanism remains to be selected; it must preserve a stable fork-time view while allowing the source to continue operating and changing. VM and live-process functionality are deferred. There is no join operation: a branch sends messages and artifact references, and the recipient imports what it wants. The fork is:

- Session: inherit the transcript by default, with a candidate fresh-context mode below; carry the applicable session state and start a fresh executor.
- Filesystem: create a branch workspace that is a CoW view of the parent's workspace. The branch can write only inside its own directory; everything inherited from the parent is read-only.
- Visibility: branch directories live under a runtime-managed cache path, not in the project; loom_status() shows them on request; GC reclaims them.
- Lifecycle: end, message, stop. No merge step.

Context modes (candidate interface, also useful as an ablation):
- Inherited context: retain the session's accumulated understanding and evidence. The parent may simply ask for another continuation; it need not identify a specialist or specify the missing knowledge.
- Fresh context: retain the original task, environment guarantees, budget, and artifact access while omitting the parent's reasoning history. This can be useful when uncertainty is high or the agent suspects its current line of reasoning is a wild goose chase. A narrow delegation brief is not required.

Both modes fork the same executable workspace for a comparison of context inheritance. Fresh context does not undo filesystem changes. The swarm can learn which mode to use, what additional context to communicate, and how to combine the resulting evidence. The ablation can therefore become a policy choice rather than remaining only an evaluation setting.

Write isolation:
- Mount namespace: expose a stable fork-time base read-only, then mount the branch's writable layer over it (overlayfs upperdir) or bind the branch subvolume writable. The process cwd is the merged view; writes land only in the branch's upper or subvolume.
- btrfs: the parent subvolume snapshot is read-only (`btrfs property set <snap> ro true`); the branch gets a writable snapshot. Snapshot of a snapshot gives recursive block-level CoW.
- overlayfs: lowerdir must be an immutable capture of the parent's fork-time workspace; a read-only view of a still-changing source is insufficient. upperdir is the branch directory, workdir is branch scratch, and the merged mount is the cwd. How to capture that base cheaply without disrupting the source is part of backend selection.
- Access control: run the branch process as a user or namespace that cannot write the parent or base; mount the host project read-only; no shared writable bind mounts. The branch's writable set is exactly its upper or subvolume.
- External side effects still escape: network, shared services, host-mounted sockets. Isolate network per branch or treat the external state as shared.

CoW level:
- btrfs subvolume snapshots: share file extents through CoW and support snapshots of snapshots. A candidate if a btrfs volume or loopback image is available; measure snapshot cost and effects on active source operations before selecting it.
- overlayfs or fuse-overlayfs: file-level copy-up, rootless, fine for source trees, bad for large files or datasets.
- XFS reflink: block-level, needs XFS.

Block-level CoW on the existing disk (verified on this host): a sparse btrfs loopback image on the existing ext4, mounted through a privileged storage container with a shared bind mount. Rootless user namespaces are blocked here by AppArmor (apparmor_restrict_unprivileged_userns=1), so unshare and rootless podman cannot mount btrfs; rootful Docker can, and the user is in the docker group. Verified inside a privileged container: mkfs.btrfs on a 256 MB sparse file, mount -o loop, subvolume create and snapshot. Verified propagation to the host with --mount type=bind,source=<host dir>,target=<mount>,bind-propagation=rshared; the host then sees the directory as btrfs and can create snapshots. The runtime can stay on the host; the container is only the mount provider. Caveats: the sidecar must stay alive or the mount disappears; the loop file cannot shrink easily, so size it generously; docker-group access is root-equivalent, so this is a trust boundary; keep the sidecar minimal and offline.

GC:
- Tree-aware: a parent's layer cannot be deleted while a child references it. Delete ended leaves; archive artifacts before deletion; compact deep chains when lookup cost grows.
- Space accounting: btrfs qgroups or compsize; overlay usage is approximate.
- Crash-safe: mark branches orphaned on startup and reclaim them.

What it does not solve:
- Live processes, in-memory state, warm page cache, exact mid-flight state. Add a service manifest to restart declared services; stateful services need per-branch instances or dump/restore.

Tests:
- Write in the child, fork a grandchild, read the write; the parent must not see it.
- Change the parent after a fork; the child must retain its fork-time contents. Check that existing source operations continue correctly across capture.
- Attempt to write outside the branch directory and fail.
- Shared blocks are not duplicated; fork latency scales with file count, not data size; cleanup leaves no residue; nested depth and large-file behavior.

5.1 Fork transparency and explicit branch identity

Fork transparency means that inherited executable state is ready to use within the backend's declared guarantees. The child receives its branch identity, context mode, remaining budget, and environment guarantees automatically. Its purpose may be open-ended; the parent need not supply a detailed assignment. The runtime defines where the copied transcript resumes and which fork result the child sees. Provenance remains in the runtime log, and loom_status() provides further detail on demand.

The first version provides session and filesystem continuity with a fresh executor. A later VM backend may also preserve running processes and listening ports. The following VM-specific seam handling is a deferred design target.

Why this matters:
- The action space stays small: fork, message, end. There is no setup_branch ritual, dependency reinstall, server restart, or reconnect step for the model to learn or fail.
- Credit assignment is cleaner: a branch failure is due to its decisions, not a setup mistake.
- Fixed-N and adaptive branches start from the same environment, so the comparison is fair.
- Training data does not include environment-management noise, which would otherwise teach a different skill.
- The complexity moves into deterministic runtime code, which is testable and needs no training data.

The runtime owns the seams:
- Per-branch network namespace with the same addresses and ports; a reconnect proxy re-establishes external connections underneath.
- In-guest loopback connections are preserved: both endpoints are in the snapshot. Host port-forwards, host-mounted Unix sockets, vsock, and host-run services cross the boundary and are re-established per branch.
- Stable hostname, cwd, environment, and process tree.
- Reseeded RNG and a defined clock policy; two branches must not share entropy or assume wall-clock continuity.
- External shared state is isolated per branch (per-branch service instances, database snapshots) or surfaced honestly. Transparency applies to the inside of the machine, not the outside world.
- Infrastructure failures (snapshot, restore, reconnect) are recorded separately and excluded from policy training.

Conformance: every backend declares which guarantees it provides. A worktree backend is a degraded implementation: it can match the transcript and files, but not running processes or ports. Train on a backend whose guarantees match the tasks; do not let the policy learn backend-specific rituals.

5.2 When a VM fork is not worth it (the worktree backend)

For bounded coding tasks, a worktree with explicit state capture is one candidate for the filesystem MVP. Choose the mechanism through the snapshot research in §15.2:

- Copy the session history; create a git worktree at the current commit; carry uncommitted and ignored state with a stash/diff plus a prepared image, or copy the working tree; start a fresh container or process from the prepared image; run a reconnect hook.
- Preserves history, tracked files, dirty state (with the copy), dependencies baked into the image, and tool availability. Does not preserve running processes, in-memory state, warm page cache, or external connections.
- No in-progress disk or network IO exists to drop, because the branch starts a new process. This removes the entire IO-reset problem.
- The join is a diff or a set of files, which is easier to provenance and validate than an opaque memory image.

A plain git worktree is not sufficient on its own: it does not carry uncommitted changes or ignored files (node_modules, .venv, build outputs), and it shares the object store and refs with the parent. Carry the dirty state explicitly, bake dependencies into the image, and give each worktree a unique branch or detached HEAD.

Escalate only on measurement:
- Worktree plus fresh container: a candidate for bounded tasks and Stage 0 prompt learning, provided dirty state is captured and the source can keep operating.
- Overlay or reflink workspace plus fresh container: when dependency install or checkout dominates branch cost; preserves files and caches, still no processes.
- VM snapshot fork: when live processes, in-memory state, or warm page cache are a large fraction of task time, or when full process and network isolation is required.

Decision rule: measure setup time per branch as a fraction of total branch time. If it is small, use the worktree. If it is large but processes are restartable, use the overlay. If processes carry state the task needs, use the VM. Record which backend produced each branch; the policy should see the guarantee set, because it changes what the model can assume (for example, whether a server is still running).

For the VM path, the IO policy is: quiesce the session at a turn boundary, flush and drain disk writes, drop external network connections, snapshot, restore, then run the reconnect hook. Loopback connections whose both endpoints are inside the guest are captured in the snapshot and survive; the criterion is the VM boundary, not the address family. A Unix socket to a host-mounted path, a host port-forward, vsock, or a connection to a host-run service crosses the boundary and must be re-established. Do not discard dirty disk writes without flushing; drop external network, not disk or in-guest loopback.

5.3 Prior art and the write-isolation recipe

Several projects already implement parts of this fork. Reuse one rather than building a filesystem.

Write isolation (kernel-enforced, no custom filesystem needed):
- Run the branch process in its own mount namespace. Bind the parent or base read-only; bind only the branch's writable layer or subvolume read-write; make everything else read-only or absent. This is the property BranchFS uses: each agent gets a mount namespace with only its @branch path as the workspace root.
- Add a user namespace and a distinct UID so the branch cannot write parent-owned paths even if a mount is misconfigured.
- Add Landlock and seccomp (for example sandlock) for filesystem and syscall confinement. This is defense in depth, not the primary mechanism.
- Keep per-branch /tmp, /dev/shm, and cache directories; never share a writable bind mount. Host mounts are external state and are not forked.
- Test: writing outside the branch directory must fail with EROFS or EACCES, including through symlinks, `..`, and absolute paths.
- Local tools available: bwrap, unshare, newuidmap, fuse-overlayfs. No root required for the user-namespace path.

Prior art:
- BranchFS / BranchContext (multikernel; MIT / Apache-2.0; arXiv 2602.08199, ASPLOS 2026 Agentic OS Workshop). The closest primitive: FUSE copy-on-write filesystem, O(1) branch creation (under 350 microseconds, independent of base size), nested branches, per-branch mount namespace isolation, process groups, no root. It has commit-to-parent, first-commit-wins, sibling invalidation, and a frozen origin, which do not match the message-passing, no-join model; borrow the filesystem and isolation design, not the lifecycle.
- LayerFS (Ephemeral-AI-Lab; MIT; 2.7k stars). Ephemeral workspaces over shared committed history, recursive branches, content-addressed deduplication, instant bootstrap with dependencies, FUSE plus SQLite. Commit/merge oriented, but a branch is a writable workspace and can be read by others; message passing can replace merge. Heavier than needed for a first MVP.
- simgit (MIT). Copy-on-write git worktrees via reflink or fuse-overlayfs; an extra worktree costs metadata, not a copy of the tree; ephemeral GC; no daemon. The closest match to the worktree MVP, but git-only and no process state.
- Waypoint (Apache-2.0). Branchable agent containers using CRIU plus OverlayFS: checkpoint a running sandbox (files, memory, live terminal sessions) and fork it into many live copies. The closest match to the full session fork without microVMs; requires root, Linux, and CRIU 4.0+ on aarch64.
- pVisor (Apache-2.0). Staged workspaces with review/apply/drop and a VM-per-container mode; not a fork, but relevant for isolation and review.
- Sandlock (Apache-2.0). Landlock plus seccomp process sandbox with a COW working directory, no root, about 5 ms startup. The confinement layer for a fork, not a branching tool.
- Others: getkern/kern (rootless container runtime for agent tool calls), Trail (operation database for worktrees), Grove (multiple agents on git worktrees).

Fit: the message-passing model needs a writable branch directory with a read-only parent view, plus read access to the branch from the parent. It does not need commit-to-parent. simgit gives that for git repos today; BranchFS gives the general filesystem primitive but its lifecycle is commit-oriented; LayerFS gives the substrate but expects commits; Waypoint gives live state but needs root and CRIU. Start by wrapping simgit or BranchFS, expose only fork/discard/read, and let messages carry artifact references. Do not implement merge.

6. Join protocol: message-based integration

Join is not a merge. A branch that elects to stop emits a summary to its parent and to subscribed peers; recipients decide what to import. Concrete contract:

- end(summary, artifacts, status): the branch stops; the runtime records an emission with provenance, cost, and artifact references, and keeps the branch snapshot readable.
- send(branch, message) / broadcast(message) (opt-in subscriptions only): delivery to an inbox by default; the recipient sees it at its next turn. An interrupt flag delivers at the next tool boundary, never mid-generation. consult(branch, question) forks the recipient to deliberate and return a recommendation without committing its state.
- import_artifact(branch, path|patch): copies files or applies a patch into the recipient's filesystem with an explicit conflict policy; validate by running tests; record the source emission and content hash.
- loom_status(): a compact table of branches (id, goal, status, last emission, cost, artifact references), never full transcripts. This is the parent's working model of the loom and the main defense against context blow-up in small models.
- Runtime rules: a branch cannot kill a peer; it may request_stop. A parent cannot end with live children unless it explicitly orphans them (reparent to grandparent or root). Crashed or timed-out branches get synthetic emissions (exit status, artifacts, partial summary). Quiescence and timeout prevent deadlock. Budget is visible to the policy and enforced by the runtime.

This keeps the minimal-emission discipline: the summary is the message, artifacts are pulled by reference, and validation is the acceptance test. Every join decision is a typed tool call, so it can be prompted and trained.

7. Harness support for message passing

Verified:
- OMP: first-class peer messaging through hub (send, wait, inbox, list, broadcast, replyTo, await). Subagents are addressable peers; parked agents revive on a direct send; messages are delivered as non-interrupting asides while running and start a turn when idle. OMP also has task subagents with filesystem isolation (task.isolation.backend: overlayfs, fuse-overlayfs, btrfs, reflink, zfs, apfs, block-clone, rcopy), batch fan-out (task.batch), parking (task.agentIdleTtlMs), and artifacts (agent://, history://). Gap: /fork copies the session transcript and artifacts but not the filesystem; task(isolated) isolates the filesystem but starts a fresh context and is torn down at completion. The combined session-plus-environment fork is the missing primitive.
- Claude Code: agent teams (experimental) with per-agent mailboxes, SendMessage, ListAgents, shared task lists, and direct teammate messaging; cross-session messaging between local sessions and across machines. Named subagents can message each other. Gap: worktrees are git checkouts, not CoW filesystem forks; session fork and environment isolation are separate features.
- OpenCode: subagents and child sessions; no first-class peer messaging.
- Codex, Gemini CLI, Cursor, Aider, and the other harnesses in plan-delivery: parent-child delegation or background tasks; no first-class peer messaging verified.

Implication: build the elastic harness on OMP first. It already supplies messaging, filesystem isolation backends (including fuse-overlayfs), fan-out, parking, and artifacts. Add a fork tool that creates the session continuation, snapshots the workspace through the selected mechanism, and registers the child in the hub; the rest is prompt and policy. Claude Code is the alternative if agent teams are preferred, but its environment fork is a worktree, not CoW.

7.1 OMP copy lifecycle and access

OMP has two separate copies:
- /fork copies the session JSONL, a new header (new id, parentSession), and the artifacts directory into a new session namespace; cwd and workspace are unchanged. The fork persists as a normal session until /drop deletes it; there is no automatic GC.
- task(isolated) creates a private workspace through pi-iso: kernel overlay with fuse-overlayfs/fusermount fallback on Linux, APFS/Btrfs/ZFS/reflink clones, ProjFS, or recursive copy. The subagent gets a fresh context, runs in that workspace, then commits to a branch (omp/task/<id>) or captures <id>.patch, and the workspace is always cleaned up. Isolated agents are torn down at completion and are not revivable; the transcript stays readable via history://.
- Non-isolated subagents share the parent cwd and are kept alive. Idle agents park after task.agentIdleTtlMs (7 min default), keeping the AgentRef and session JSONL, and revive on a hub message or an Agent Hub action.

Access:
- The isolated workspace is private to the branch. Other agents can read its output (agent://<id>), transcript (history://<id>), patch (<id>.patch), or merged branch, but not the live workspace. local:// is shared across the parent and subagents.
- The hub roster is process-global: peers are agents in the same omp process/session tree. hub send revives a parked agent; broadcast targets visible live peers; mailboxes cap at 100 messages. Collab guests can view transcripts and control host subagents but are not peers.

Gap for the elastic harness: OMP's isolated branches are not revivable, and its revivable branches are not isolated. The combined fork needs a new lifecycle: retain the branch workspace, register the branch as a revivable peer, and GC on end or space pressure according to the selected backend's dependencies. That is the tool to add; the messaging, isolation, fan-out, and parking primitives already exist.

8. Baselines, targets, and interpretation

For fixed N, begin with five independent attempts. Record both whether any candidate passes the evaluator (pass-at-five) and the correctness of the one answer an implementable model-and-tools selection procedure actually delivers. Give selection procedures only the evidence available during execution. Held-out evaluator results remain evaluation evidence.

Pass-at-five is an engineering reference and performance target, not the sole definition of success. The adaptive system should work toward matching or exceeding that benefit, handling its own selection and integration, and reducing cost relative to fixed-N execution. It may also outperform independent attempts by combining discoveries from different branches.

Diagnose failures separately: no branch produced a correct solution; a correct solution existed but was not selected; or incorporation damaged a useful result. Use these distinctions to improve generation, coordination, selection, or merging. Negative measurements remain meaningful even when they motivate further iterations rather than abandoning the research direction.

Measure delivered correctness, total cost/computation, and elapsed time over several resource budgets. A useful result may extend the Pareto frontier through better accuracy, lower cost, or lower latency. Slightly lower accuracy can still be valuable when the cost or latency improvement makes the configuration competitive. Score the delivered artifact, and account for every branch's work. Report training/data-generation costs separately from deployment costs, while keeping both inside the initial trial's total budget.

Dollar cost is a primary axis. A particularly interesting outcome is equal delivered correctness and task latency while serving inference at a lower dollars-per-token point. Report total dollars per delivered result alongside input/output token counts, cache usage, effective token prices, environment cost, and selection/communication/integration work. Lower token prices and lower task cost are separate measurements: additional tokens must be included in the latter. For local serving, state the hardware-cost basis and measure utilization and queueing; token counts alone cannot establish the economic result. Model and task selection start after the tool is available, using ordinary tasks with a best-of-N benefit rather than requiring a curated set of decomposition opportunities.

Part II — Deferred and longer-term work

10. Deferred training track

Deferred training track (Stage A onward). Stage 0 informs the training design; successful prompt-only organization is not a prerequisite. Begin with one training task family: coding, with multiple task instances and separate training, development, and held-out evaluation splits. Multi-task training is a possible later step. The initial experiment uses full student fine-tuning; adapters and Jev are separate options.

First establish tool-enabled coding baselines. Qwen2.5-Coder-0.5B-Instruct is a candidate for a cheap initial probe; 1.5–3B alternatives are also candidates. Select executable coding and repair tasks with reliable outcome checks. Start with bounded tasks and expand to repository work; investigate ProgramBench when the system is ready for that scale.

Stage A: plain DeepSeek distillation and container infrastructure, developed in parallel. Generate ordinary DeepSeek coding outputs or serial tool-use traces on training-split tasks, without loom interventions, and fully fine-tune the student on them. This checks data collection, formatting, training, checkpoint export, inference, and evaluation. Preserve it as the stronger-teacher distillation control. Independently build and validate the forkable container/session infrastructure and join semantics. The plain-distillation run need not wait for the loom runtime.

Stage B: DeepSeek-guided fork/join, after both Stage A tracks work. At execution checkpoints, let DeepSeek choose whether and how to intervene. It supplies a continuation, including legal fork/join actions where useful, using only information available at that checkpoint. Execute those actions and resume the weaker model. Record actual tool results and branch outcomes rather than inventing successful continuations. Teacher intervention uses the same session capabilities; it does not introduce authority to terminate peers. Train a separate student from the same initial checkpoint and compare it with the matched plain-distillation control.

Candidate prompts can govern the choice of insertion points and insertions. Begin with a small set of strategies. A genetic search can mutate and select strategy prompts according to the completed looms they produce. Search on training/development tasks, using delivered correctness and total resource consumption as fitness. Count unsuccessful branches, search, filtering, and teacher calls. Use repeated evaluations where needed to distinguish improvements from sampling noise.

Stage C: same-model self-bootstrapping. Replace DeepSeek's data-generation and intervention role with the same frozen model checkpoint being improved. Compare ordinary self-generated serial traces with self-generated loom traces. Keep stronger-model proposals, intervention selection, and learned judging out of this condition; executable training-task feedback remains available. Log the source of all decisions so stronger-teacher assistance cannot silently enter the self-bootstrap result. This is the central control for determining whether gains can arise without importing a stronger teacher's capabilities.

For every condition, fine-tune all student weights on selected useful decision and continuation examples. Preserve useful failed experiments followed by appropriate revision or self-stopping. Do not indiscriminately imitate every action from a successful loom. Retain ordinary coding behavior and check for regressions. Derive each training example from information that was actually available to its session.

Evaluate trained students without DeepSeek or other extra decision models on held-out tasks. A single successful self-bootstrap round demonstrates self-training or self-distillation. A claim of recursive self-improvement requires subsequent improved checkpoints to generate useful training data for later generations, with sustained measured gains under comparable budgets.

Model size is an experimental variable. Being barely capable of writing code may be insufficient for recognizing when to fork, evaluating other branches, and integrating results. A negative result on a tiny student must lead to diagnosis and consideration of larger students, rather than an automatic rejection of the architecture. Keep larger-model follow-ups explicit, within separately established resource budgets.

10.1 Training baselines and controls

Measure an untrained single session, the untrained student with access to the loom primitives, a fixed-N implementation, and the trained adaptive loom. Use the same task starts and comparable tools and resource budgets. Teacher-assisted execution is a separate diagnostic condition.

The training controls form a two-by-two comparison: DeepSeek-generated ordinary traces; DeepSeek-guided loom traces; same-model ordinary traces; same-model loom traces. Begin each matched training run from the identical student checkpoint. Match processed training tokens, supervised target-token counts as closely as practical, optimizer settings, update budgets, task distributions, and evaluation resources; disclose any remaining differences. Ordinary DeepSeek outputs on benchmark training tasks must be a real baseline, so a gain over the untouched student alone cannot be attributed to loom training.

Also account separately for trace-generation, candidate-search, filtering, and selection costs. Use a matched generation-budget comparison to check whether gains come simply from spending more compute or selecting more data. The same-model serial versus same-model loom comparison isolates organization from stronger-teacher transfer, subject to these remaining controls. Stage the four conditions within the budget rather than launching all of them before the pipeline works.

10.2 Generalization and curriculum

First train on the single coding task family and measure held-out coding performance. Then evaluate the frozen trained checkpoint on unseen task families without further training, against the same untrained and plain-fine-tuned controls. Candidate transfer settings include tool-based data analysis, environment troubleshooting, and evidence-gathering tasks with verifiable outcomes. Retain the same fork/join interface while varying task content and, later, tool sets and horizons. Report absolute performance and improvement over the controls; a model with no underlying competence in a transfer task may give an inconclusive result.

The aim is to test whether the model learned reusable organization and planning behavior, beyond benchmark-specific coding patterns or generic distillation gains. Transfer across several settings would support that hypothesis without establishing universal planning competence.

Add automated task perturbations where a reliable validity check is available. Begin with inexpensive, seeded transformations of coding tasks. For variants intended to preserve behavior, consider consistent identifier renaming, formatting changes, reordering independent definitions, and equivalent task descriptions. Verify that transformations preserve the task contract; reflection, public APIs, imports, or order-dependent execution can make superficially harmless changes invalid.

Also create controlled variants that change the required solution: different input ranges, boundary conditions, data schemas, or requirements. Update reference solutions and tests together, or derive expected behavior from a trusted executable specification or checkable relation between the original and transformed tasks. These variants test whether the system responds to changed evidence and requirements rather than replaying a familiar solution. Later, introduce controlled execution perturbations, such as new evidence arriving at a checkpoint, to test whether fork/join behavior adapts to the situation. Keep these distinct from ordinary difficulty increases.

Split source tasks before creating variants. Keep every original and all of its variants in the same split, and reserve some transformation families or compositions for evaluation. Version the generators, record random seeds, and validate variants before comparing model results. Prefer deterministic transformations initially; if a model generates a variant, record its provenance and validate it independently. Evaluation variants and their answers must not enter trace generation, filtering, prompt search, or training. Training-time augmentation is a later, separately controlled experiment.

Run original/perturbed task pairs across the untrained, plain-distillation, guided-loom, self-training, and self-loom conditions as those checkpoints become available, with matched resource budgets. Measure delivered correctness, the change under perturbation, cost, latency, and relevant fork/join decisions. For changed-requirement variants, measure whether the output changes appropriately; unchanged output is not the desired invariant. Treat variants of one source task as related observations when estimating uncertainty. Robustness differences can reveal reliance on benchmark wording or teacher-specific patterns, but perturbations alone cannot prove or rule out distillation. Interpret them together with the matched teacher-source controls and the same-model experiment.

If single-task training does not transfer, test a curriculum containing a few task families. Keep some task families entirely outside the training mixture. Separate transfer-development tasks used to choose the curriculum from untouched final evaluations, and account for the added training budget. Start with one task family; do not make multi-task training a prerequisite for the first trial.

The $1,000 ceiling below applies to the full trial if the deferred training track is pursued; the prompt-only stage should cost far less.

The initial trial must cost less than $1,000 in total, including DeepSeek calls, any rentals, storage, environments, training, and evaluation. Use the existing Spark for full fine-tuning and the RTX 3080 Ti and RTX 3070 as possible independent student-inference workers. Confirm the Spark's configuration and the available CPU RAM/disk capacity for forked environments. In the DeepSeek phases, plan for up to ten concurrent API sessions, with explicit token/spending caps and a bounded initial run. The self-bootstrap condition uses the student checkpoint for those model decisions. Reserve resources for matched controls and evaluation; do not spend the entire budget on one trained condition.

A previously discussed costing placeholder was 25,000 examples averaging 4,000 processed tokens, or 100 million training tokens for one pass. AsyncThink's roughly 25,000–43,000 bootstrap pairs supplied a scale reference; its later reinforcement-learning stage and different tasks mean this is not evidence that our task needs or will succeed with that amount of data.

The user explicitly questioned whether 4,000 tokens is adequate for these coding tasks. Measure representative real session contexts and preserve the information needed for decisions. Count repeated context processing, examples from all branches, training passes, and full-loom generation/evaluation. Recompute memory and time estimates from those measurements. 10.4 Elicitation as a teacher-free labeler

At each decision point, the runtime pauses and asks a generic introspection question: here are reasons a session might branch (uncertainty about the approach, several plausible strategies, independent subproblems, a result that is expensive to verify, remaining budget), and here are reasons not to (the marginal branch is unlikely to pay for itself, the evidence is already sufficient, the budget is nearly spent). Do you want to branch, and why? The model answers in the trace; if yes, it forks from the current state.

- The prompt is generic, not task-specific. It presents the space of reasons, not the answer. Including reasons against is required; without them the scaffold teaches an always-fork bias.
- The elicited reasoning, the decision, and the outcome form the training trace. Train the model to produce the introspection and the decision without the scaffold. The scaffold is a context-distillation device: the policy internalizes the question it was asked.
- The signal is the decision plus the outcome. The decision is the label; delivered correctness and cost filter and weight it. Without an outcome signal, elicitation only teaches the model to answer the question, not to answer it well.
- Keep no-branch decisions in the data and balance them against forks. Measure the fork rate against a neutral prompt to detect scaffold-induced over-branching.

10.5 Teacher versus elicitation: checkpoint economics

- Teacher, retrospective: it inspects the trace after the fact and inserts at a point it judges reasonable. Inserting at step k requires the state of every session in the task at step k, so it must roll back all sessions to the insertion point. Storage is O(sessions x steps x state) and grows with the loom; as looms get more complex the checkpoint set grows exponentially with the tree, not just the compute. Sparse checkpoints reduce storage but limit where the teacher can insert.
- Elicitation, prospective: it asks at the current frontier; a yes forks from the present state. There is no rollback and no historical checkpoint beyond what the baseline loom already keeps at fork points. The cost is latency proportional to elicitation frequency, not storage.
- Teacher has hindsight and can label points the student skipped; elicitation has foresight and can only ask now. Use the teacher to bootstrap a small seed of good decisions, and elicitation to scale the data. Do not run the teacher over the full loom.
- Hybrid: elicit online for most decisions; retain checkpoints and use the teacher only on a small subset where retrospective correction is worth the storage.

10.6 Deferred teacher flow

Do not build the programmatic teacher flow or the full historical checkpointing until elicitation results show where it is needed. Elicitation is cheap in storage and expensive only in latency; the teacher is the reverse. Use the teacher later, on the small subset of decisions elicitation gets wrong, with checkpoints retained only for that subset.

A weak model may branch too often or too rarely at first; the state space explodes and the marginal benefit is small or negative. If elicitation alone does not produce a usable signal, the teacher bootstraps a small seed and elicitation scales from there. This stage uses session and filesystem checkpoints, with the backend chosen through systems research. VM functionality is deferred to a later version.

11. Fork mechanisms: deferred VM design

The following memory-layer design is a candidate for a later VM backend, not an MVP requirement. Its target is to share read-only physical pages between a child and its immediate parent, where the parent may itself be a COW layer over its own parent. The memory is a tree of layers, not a star of children over one host snapshot: a fork of a fork must see the intermediate branch's changes and share that branch's pages read-only, copying only pages written after that fork.

- Each fork creates a memory layer whose reads fall through to the parent layer and whose writes allocate in the child layer. Unchanged pages are shared transitively: a grandchild reading a page unchanged since the root resolves to the same host physical page; reading a page the child wrote resolves to the child's private page.
- Guest page tables are ordinary guest memory, so they are layered like any other page. The host EPT/NPT is per-VM and is the one mapping that is not shared; it is small relative to RAM and can be populated lazily. Sharing EPT across VMs is not commodity.
- The disk uses the same layered structure: reflink or overlayfs lower layers, with each branch's writes in its own upper layer.
- Layers compose recursively; reads walk the chain. Bound the depth and compact offline, because deep chains increase fault latency and bookkeeping.

Containers do not provide this. CRIU, gVisor checkpoint/restore, and the Kubernetes container checkpoint API copy memory and restore into a new container; there is no COW sharing and no cheap fork. Docker/Podman checkpoint is a migration primitive, not a fork primitive. Process-level fork COWs data pages but copies page tables; page-table COW needs kernel changes. Use microVM fork, where the guest page tables are just COW memory.

Verified implementations (2026-11), classified by whether they layer relative to the immediate parent or re-base on the child:
- Cloud Hypervisor (layers): memory_restore_mode=copyonwrite maps the parent snapshot COW; snapshotting a VM restored that way copies the restore source with a reflink and writes only pages changed since the restore. That is a new layer relative to the immediate parent, recursively. The snapshot and restore source must stay on the same reflink-capable filesystem and the restore source must remain unchanged.
- Firecracker (layers, manual): diff snapshots are layers relative to the last snapshot of the same VM; snapshot-editor rebase merges them. A fork of a fork can be expressed as a diff layer on the child, but diff snapshots are developer preview and chain management is manual; verify resumability of the chain.
- SnowFlock (layers, research): lazy state replication gives each child a COW view of its parent; children of children share the child's state. The classic recursive design, cross-host.
- microsandbox (verify): msb fork / fork_many with --cow-mem; per-child memory sharing and a reusable local memory cache are documented, but not whether a fork of a fork layers on the child or re-bases by snapshotting it. Test this before relying on the property.
- E2B (re-bases): fork snapshots the source and boots N children; a fork of a fork likely snapshots the child, materializing its private pages, rather than adding a transitive layer. Verify if chain semantics matter.
- Firecracker full snapshots, PandaStack, Daytona hot snapshots, Apple VZ save/restore, Arrakis: snapshot/restore primitives; each restore is relative to a stored image, not a chain of live layers. They give fast fork from one checkpoint, not recursive COW.
- Apple Virtualization.framework: saveMachineStateTo / restoreMachineStateFrom (macOS 14+) for a paused VM; no documented COW sharing across restores. Relevant to Omerta's Swift nodes, not a high-fan-out fork primitive.
- Modal: filesystem snapshots only; no memory fork.
- gVisor, CRIU / Kubernetes: checkpoint/restore with memory copy; no COW layers. gVisor has background restore and zero-page exclusion; Kubernetes container checkpoint is beta since 1.30.
- agent-sandbox: Kubernetes Sandbox CRD, pause/resume and warm pools; orchestrator only, no fork.
- Blaxel: microVM standby resume under 25 ms; no fork documented.

Costs and hazards:
- Snapshot capture, not restore, dominates a fork from a running branch: full capture faults and writes all RAM; diff capture writes only dirty pages. Fork from a clean checkpoint at a tool boundary.
- The host EPT is per fork and is the one mapping cost that is not shared; it is small relative to RAM and can be populated lazily. Sharing EPT across VMs is not commodity.
- External side effects do not fork: sockets, shared mounts, remote APIs, git remotes. Give each branch a network namespace and egress policy, re-establish connections after restore, and record external effects.
- RNG and clocks duplicate across forks; reseed where available and avoid absolute-time assumptions.
- Memory accounting must count shared pages once and charge unique pages per branch; otherwise fan-out cost is overstated and budgets are wrong.
- Snapshot files contain all memory, including secrets; restrict access and encrypt at rest.
- Cross-host forks must ship memory and disk; keep forks on the parent's host and send only emissions across machines.
- CPU feature and GIC compatibility constrain restore across hosts.
- GPU state does not fork cleanly. Keep model inference outside the forked session; fork only the tool and environment state.

Verification recipe for the layered property (run before committing to a backend):
1. In the child, write a known pattern to a page that was unchanged at the child's fork, then fork a grandchild. The grandchild must read the child's pattern, not the root's. This catches re-basing that silently drops intermediate state.
2. Measure host shared and private memory (PSS-like accounting, or COW fault counts) before and after forking N grandchildren. Pages the child never wrote must not be duplicated; the grandchild's private memory must scale with its own writes, not with the child's private set.
3. Measure fork latency against dirty MB since the parent layer. A layered backend's grandchild fork cost scales with the child's dirty pages; a re-basing backend scales with the child's total private memory.
4. Fork a chain at least three deep and read pages written at each level; then compact and re-read. This catches chain-depth and compaction bugs.

Research for the later VM backend: investigate Cloud Hypervisor, Firecracker, microsandbox, E2B, and smolvm against the conformance recipe above. Verify cross-generation physical-memory sharing separately from filesystem reflinks or shared restores of one snapshot; the mechanism descriptions alone do not establish the stronger property. Instrument fork latency versus dirty MB, fan-out, shared versus private pages, and emission bytes. This research does not gate the filesystem MVP.

11.1 Scaling to thousands of branches

Fork transparency is what makes a large loom affordable. With it, the marginal cost of a branch is its unique dirty pages plus its vCPU time, not a full environment bootstrap, and the model does not manage setup per branch.

Rough per-branch cost for a small microVM:
- Shared pages: counted once across the tree, read-only.
- Unique memory: pages the branch writes; this is the dominant marginal cost.
- Per-VM overhead: kernel and device state, EPT/NPT (single-digit MB for a few GB of guest RAM), vCPU thread(s), network namespace or TAP, file descriptors, snapshot-layer metadata.
- Snapshot storage: one base plus per-branch diff layers; compact periodically.

At 1,000 branches, the limits are unique memory, CPU overcommit, host thread/FD/TAP limits, snapshot storage, and the pause cost of snapshotting an active parent. Thousands of branches fit on one large host only if most branches are small and short-lived; otherwise the loom spans hosts.

Requirements at that scale:
- Same-host placement for COW locality. Cross-host forks ship memory and disk and are for capacity, not the default. Only emissions cross hosts.
- A recursive tree, not a flat fan-out: branches fork branches, and layered COW keeps the tree affordable. Cache a snapshot when several children fork from the same point.
- Parking and eviction: pause idle branches, free vCPU and RAM, resume on message or need. At scale, most branches are idle at any moment.
- Admission control and accounting: per-branch caps, shared-page accounting, deny or defer forks when the host budget is exhausted.
- Hierarchical loom_status: summarized per subtree; full transcripts stay in the log, never in context.
- Failure handling: synthetic emissions for crashes and timeouts, orphan reparenting, retries. At 1,000 branches, failures are normal.
- Security: per-branch network isolation, encrypted snapshots, verified cleanup.
- Multi-host scheduler: place a fork near its parent; treat cross-host placement as a migration.

The bottleneck shifts from fork cost to inference and coordination. A thousand branches only pay off if most are short-lived and the policy prunes early; the value-of-computation decision becomes the main learned skill.

Hardware link: per-node fork plus emissions-only networking is the C7/C10 shape. Omerta's VM-per-task model becomes fork-per-branch if the provider exposes snapshot/restore; the Linux KVM path (Firecracker/Cloud Hypervisor) has the COW primitive, while Apple Virtualization.framework save/restore does not share memory across restores.

12. Broader hypothesis

The larger bet is that learning to organize branches becomes learning how to investigate a problem. The system can generate alternatives, run experiments to discriminate among them, revise assumptions, exchange evidence, and reconsider which possibilities deserve more computation. A branch can implement a solution or investigate whether the problem itself has been framed correctly.

The “space of all plans” is the ideal search domain, explored under resource constraints. Useful alternatives and distinctions can be discovered during execution. Plans remain revisable resources. Work ends when the actual result satisfies the relevant acceptance criteria, which may be clarified through feedback during the task; completing an earlier written plan is not sufficient by itself.

The computer-architecture analogy is dynamic task parallelism: a session discovers additional work and creates peers with the same capabilities. Management can recurse without a special manager class. The economic conjecture is that useful additional parallel computation can offer better returns than strengthening one execution stream. No universal exponential cost law is assumed.

A further hypothesis is that learned organization can let capable systems exploit many modest computers with cheaper interconnects. That requires substantial local work between exchanges and sensible decisions about placement, state transfer, and communication. These are future hypotheses, not established results of the initial experiment. Suchman's work inspired the discussion; the branch-management architecture is our engineering extension.

12.1 Separate architecture requiring no training

Keep a Jev-assisted variant as a distinct experiment. Each session can consult the same classifier about concrete available fork/join actions. The session or surrounding software supplies candidate actions and their parameters. Jev selects or scores them; the runtime records an explicit continuation in the trace, performs the corresponding action, and resumes execution.

This tests whether a general-purpose decision model can provide useful organization without student training. It is not a privileged manager. Compare it with the untrained and trained students, counting classifier input processing and all branch work. If it works, a learned replacement or distilled decision policy becomes a possible cost optimization.

12.2 Follow-ups

If the deferred training track is pursued, follow the staged order: plain distillation alongside container development, DeepSeek-guided fork/join, same-model self-bootstrapping, and transfer tests. Multi-task training and repeated self-improvement generations are follow-ups informed by those results. Evaluate larger students when small-model results are inconclusive, and expand to harder repository tasks, stronger single-session baselines at matched cost, longer contexts, and the Jev-assisted architecture. Investigate adapters and other training-cost optimizations for larger models. Later study learned decision components, distributed placement, and performance across machines with limited interconnects.

Fork mechanisms and their evidence are in §5.3 and §2.1; harness messaging is in §7; OMP's copy lifecycle is in §7.1. This section records the best-of-N, verifier, and parallel-agent landscape; the reading order is in §15.2.

Landscape:
- omp-best-of (wolfiesch, MIT). OMP extension: /best-of --n 2-8, isolated CoW workspaces, LLM-as-a-Verifier ranking, winner-only patch application. Closest prior art. Fixed N, user-invoked, no mid-task fork, no peer messaging. Its bench/RESULTS.md is the cautionary tale: saturated pools, a verifier picking the failing candidate, and three evaluations tripling cost with no accuracy gain.
- LLM-as-a-Verifier (Kwok et al., arXiv 2607.05391, 3.3k stars). Continuous scores from scoring-token logprob distributions, probabilistic pivot tournament; Terminal-Bench V2 86.5%, SWE-Bench Verified 78.2%. Selection method only; no harness, fork, or policy.
- dsh-llm-as-a-verifier. The same verifier exposed as DeepSeek Harness tools: verify_compare, verify_select, verify_track.
- smolvm (smol-machines, Apache-2.0, 7k stars). Branchable microVMs: live CoW branches with processes, memory and disk, recursive sharing, disk-chain compaction, warm pools. Best full-session fork primitive; deferred backend.
- BranchFS / BranchContext, LayerFS, simgit, and Waypoint: see §5.3.
- Hail Hydra (MIT). Task-level speculative execution: cheap models draft, the orchestrator verifies or redoes. Task delegation, not session forking.
- agentbox, uzi, pro-workflow. User-orchestrated parallel coding agents in git worktrees, with inbox or board UIs. The manual version of the product.
- EnCompass (NeurIPS 2025, arXiv 2512.03571). Search over execution paths; ARC subset 4.3% to 11.7% at best-of-8 and 16.0% at best-of-36; Reflexion 35.5% to 36.1% at lower cost. Closest policy framing.
- Large Language Monkeys (arXiv 2407.21787), Snell et al. (arXiv 2408.03314), Agentless (arXiv 2407.01489), Reflexion (arXiv 2303.11366), self-consistency (arXiv 2203.11171), Tree of Thoughts (arXiv 2305.10601), LATS (arXiv 2310.04406). Repeated sampling, compute-optimal test-time scaling, sampling plus selection, and the strategy space the model may already know.
- Learning by Distilling Context (arXiv 2209.15189), STaR (arXiv 2203.14465), Quiet-STaR (arXiv 2403.09629). The elicitation-to-no-scaffold training move and its collapse risk.

Research focus: incorporate executable computer state into the loom and make organization, including selection and delivery, available to prompting and training. The references supply mechanisms and evidence for this work; no priority claim is needed. omp-best-of is a close implementation reference, and its small benchmark illustrates task and selection issues to inspect.


15. Related work additions and revised reading order (2026-11-06)

This section supplements the references in §14 and gives the reading order. The organizing question is §0.1: can copyable agents learn to organize their own computation, including branching, communication, selection, integration, and stopping? The references below supply mechanisms, learning methods, and evidence for that investigation. Establishing novelty is not a planning requirement.

The immediate dependency is systems research: choose a low-cost snapshot mechanism that lets the source continue changing, either directly or through a cheap stable copy that does not disrupt existing operations. That mechanism determines the MVP. Model and task selection follow availability of the new tool. Selection and final delivery remain deliberately open policy questions for the swarm; isolation, accounting, and execution mechanisms should support those decisions without prescribing a fixed coordinator or selector. Branch identity, budget, and environment guarantees should be explicit to each session.

Small-N best-of-N performance is a reasonable initial engineering target, not a guaranteed lower bound. Fixed-policy results are useful references, but exhaustive comparisons and a separate setup-sharing experiment are not prerequisites. Prompt-only work is the first experiment; failure to elicit useful organization does not gate the training track.

15.1 Additions and references to promote

- AsyncThink — The Era of Agentic Organization: Learning to Organize with Language Models (Chi et al., 2025). Already mentioned in §10.3 for data-volume estimates; promote it to a central conceptual reference. Its organizer dynamically assigns sub-queries to workers, incorporates their results, and learns asynchronous thinking structures through training. Read for the action protocol, learning signal, and treatment of concurrency and latency. Weft's questions include inherited executable state and recursive peers with the same capabilities; examine those differences directly rather than assuming results transfer from reasoning tasks. [Paper](https://arxiv.org/abs/2510.26658).

- Rational metareasoning — Selecting Computations: Theory and Applications (Hay, Russell, Shimony, and Tolpin, 2012), followed by Learning to Select Computations (Callaway et al., 2018). The first formalizes choosing computations by the expected value of the eventual decision minus the cost of gathering information. The second learns policies for stopping, allocation among alternatives, and planning, including the overhead of metareasoning itself. These are foundations for §0.1's learned allocation policy. Read for the objective and stopping problem; they do not require implementing a particular search heuristic in the harness. [Selecting Computations](https://aima.eecs.berkeley.edu/~russell/papers/uai12-meta.pdf), [Learning to Select Computations](https://arxiv.org/abs/1711.06892).

- GEPA — Reflective Prompt Evolution Can Outperform Reinforcement Learning (Agrawal et al., 2025). A close methodological match to Stage 0: reflect on execution trajectories, propose prompt changes, and retain complementary candidates through Pareto-based evolutionary search. Inspect the implementation before writing a custom genetic optimizer. The proposed application is to evolve the swarm's instructions for organization, including selection and integration, against delivered outcomes and costs. Compare its evaluation and population management with the existing plan-doc-eval discipline. [Paper](https://arxiv.org/abs/2507.19457), [implementation](https://github.com/gepa-ai/gepa).

- CodeMonkeys — Scaling Test-Time Compute for Software Engineering (Ehrlich et al., 2025). Combines serial code-and-test refinement with parallel candidate trajectories, then selects using generated tests and a dedicated selection trajectory. This is useful evidence about how multiple coding attempts become one delivered patch, including the work involved in testing and selection. Read its methods as possible behaviors the swarm can adopt and learn. Its fixed workflow need not become Weft's runtime policy, and its shared upfront work does not create a requirement for a separate setup-cost experiment. [Paper](https://arxiv.org/abs/2501.14723), [implementation](https://github.com/ScalingIntelligence/codemonkeys).

- CodeT — Code Generation with Generated Tests (Chen et al., 2022). Generates tests as well as code candidates and selects using execution agreement. It supplies a concrete way for agents to gather evidence about competing solutions when provided tests are incomplete. Generated tests are still fallible; their value is something to measure against withheld outcomes. For Weft, this suggests a learnable testing and comparison behavior available within the swarm. [Paper](https://arxiv.org/abs/2207.10397), [implementation](https://github.com/microsoft/CodeT).

- SWE-Search — Enhancing Software Agents with Monte Carlo Tree Search and Iterative Refinement (Antoniades et al., 2024). Combines repository-level agent execution with MCTS, numerical and qualitative evaluation, and feedback among agent roles. Read for useful exploration and evaluation patterns, along with their costs. It provides a concrete reference for investigating alternatives during execution; adopting its fixed search controller or role decomposition is not a requirement. [Paper](https://arxiv.org/abs/2410.20285).

15.2 Recommended reading order across the full list

1. Snapshot semantics and harness integration — immediate implementation dependency.

Start with [OMP](https://github.com/can1357/oh-my-pi)'s hub, task-isolation, session-fork, and lifecycle documentation, alongside the gap recorded in §7.1. Then read [BranchFS / BranchContext](https://arxiv.org/abs/2602.08199), the [Btrfs subvolume documentation](https://btrfs.readthedocs.io/en/latest/Subvolumes.html), and the [OverlayFS documentation](https://docs.kernel.org/filesystems/overlayfs.html). The specific question is how to retain a stable fork-time view while the source keeps operating and writing. A read-only mount of a changing source is not sufficient: OverlayFS documents changes to underlying filesystems while mounted as undefined behavior.

Inspect [simgit](https://github.com/abendrothj/simgit) and [LayerFS](https://github.com/Ephemeral-AI-Lab/layerfs) for reusable filesystem mechanisms. Choose the initial snapshot mechanism by source-write behavior, interruption, cost, and host compatibility. The MVP preserves session and filesystem state; live-process and VM functionality are deferred to a later version.

Consult Sandlock, pVisor, getkern/kern, and other isolation references in §5.3 as needed for the selected executor. The output of this reading is a measured filesystem mechanism choice and its guarantees. The VM and process-checkpoint literature moves to step 6.

2. Learned organization — read early to guide the interface.

Read AsyncThink, then the two metareasoning papers in §15.1, then [EnCompass](https://arxiv.org/abs/2512.03571). Together they address learned concurrency, the value of additional computation, and separating agent workflow from search over execution paths. Use them to ask which decisions the primitive should leave available to the agents. Follow with the project's minimal-sufficient-inference review and plan-mind §7b from §13 for context inheritance, emissions, and recursive invocation. This conceptual reading can proceed during systems research without delaying the first usable tool.

3. Evidence gathering, selection, and initial task design — once the tool is available.

Read CodeMonkeys, CodeT, [omp-best-of](https://github.com/wolfiesch/omp-best-of), and its [measured results](https://github.com/wolfiesch/omp-best-of/blob/main/bench/RESULTS.md). Then read [LLM-as-a-Verifier](https://arxiv.org/abs/2607.05391); inspect dsh-llm-as-a-verifier if its tool interface is useful. These readings inform what evidence the swarm can obtain and how it can decide among results. They do not assign the final decision to an external controller. Treat the small omp-best-of experiments as diagnostic examples, not a general accuracy estimate.

Follow with [Large Language Monkeys](https://arxiv.org/abs/2407.21787), [Snell et al. on scaling test-time compute](https://arxiv.org/abs/2408.03314), and [Agentless](https://arxiv.org/abs/2407.01489) for sampling, compute allocation, and coding-task practice. Use these when choosing the first models, tasks, and budgets after the tool is available. Ordinary tasks that benefit from best-of-N provide the starting point; a special task-design campaign is not required.

4. Prompt learning and behaviors the swarm can discover.

Read GEPA and the project's plan-doc-eval before building the prompt-search loop. Give the optimizer complete outcome and cost records, including the swarm's own verification, communication, and integration work. The learning target includes the whole organization policy.

Read [Reflexion](https://arxiv.org/abs/2303.11366), [self-consistency](https://arxiv.org/abs/2203.11171), [Tree of Thoughts](https://arxiv.org/abs/2305.10601), [LATS](https://arxiv.org/abs/2310.04406), and SWE-Search as a repertoire of revision, sampling, exploration, and evaluation strategies. Consult Hail Hydra for speculative delegation and agentbox, uzi, pro-workflow, Trail, and Grove for orchestration examples when a concrete interface question arises. These are sources of candidate behavior and implementation ideas; the swarm remains responsible for deciding which behavior to use.

5. Learning from traces and removing scaffolds — when preparing training.

Read [Learning by Distilling Context](https://arxiv.org/abs/2209.15189), then [STaR](https://arxiv.org/abs/2203.14465), and return to AsyncThink's training procedure. They bear on internalizing prompting, learning from generated traces, and training organization itself. Read [Quiet-STaR](https://arxiv.org/abs/2403.09629) afterward as an adjacent approach to learning useful reasoning. Use the matched teacher-source controls already in the plan to interpret gains. Prompt-only results inform the training design, including failures worth addressing; they are not a pass/fail prerequisite for this track.

6. VM state, distributed deployment, and broader architectures — later versions.

Read [smolvm's branching documentation](https://github.com/smol-machines/smolvm/blob/main/docs/branching.md), [Cloud Hypervisor's snapshot/restore documentation](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/snapshot_restore.md), Firecracker, and Waypoint/CRIU when extending the fork to live-process and memory state. Use gVisor, E2B, microsandbox, and SnowFlock as targeted comparisons. Distinguish shared disk extents from shared resident memory and verify how the source continues after a fork.

Return to the minimal-sufficient-inference review, Omerta, and SnowFlock when placement, state transfer, or communication becomes a measured constraint. Keep Petals, compound AI systems, Mixture-of-Agents, FrugalGPT, AlphaCode, distributed training, MoE, and hardware scaling as later background. CodeT is explicitly promoted to step 3. Revisit the remaining systems catalog in §11 when a chosen backend exposes a concrete limitation; completing that catalog is not required before trying the swarm.

16. Related work additions from the Claude review (2026-11-06)

This section supplements §14 and §15 and uses §15's framing. The references supply mechanisms, candidate behaviors, and evidence for a loom that includes executable computer state. They do not prescribe a coordinator, a selector, or a comparison campaign. Entries are grouped by the §15.2 step where they belong; read them after that step's existing items, in the order listed. Entries marked (abstract only) were read from abstracts, listings, or READMEs rather than full texts.

16.1 Step 1 — snapshot semantics and harness integration

- ParallelEnv — Parallel Environments for Agents (Tan, Zhang, and Zaharia, ACM CAIS 2026 demo). The closest systems reference found. At each fork, the kernel captures the agent's Docker container and starts the child from the capture while the parent continues in its original container; a pluggable scheduler decides which branches run. Read for how capture avoids disrupting the source (plain `docker commit` pauses the container by default) and for fork costs at SWE-bench scale. Its fork trigger is fixed (fork when the patch changes), and the kernel runs the SWE-bench harness at fork points and ends the other branches when tests pass. Its reported 48% at $0.50 on 100 SWE-bench Pro instances therefore depends on a golden checker. Weft leaves the fork decision, the evidence, and stopping to the swarm. (Abstract only.) [ACM](https://dl.acm.org/doi/10.1145/3786335.3813189), [CAIS listing](https://www.caisconf.org/program/2026/demos/parallel-environments-for-agents/).

- Claude Code fork agents — a possible correction to §7. Current Claude Code's Agent tool has a fork mode that inherits the full conversation, and the same call accepts an `isolation: worktree` option. Before recording session fork and environment isolation as separate features, verify whether the two compose and whether the worktree carries uncommitted and ignored state. The environment would still be a git checkout, not a CoW snapshot.

16.2 Step 2 — learned organization

- APR — Learning Adaptive Parallel Reasoning with Language Models (Pan et al., 2025). Spawn and join are model actions trained end to end with RL. The parent chooses what context each child receives and continues from the joined results. The closest learned fork/join action protocol to Weft's, without executable state. Read alongside AsyncThink for action design and reward. [Paper](https://arxiv.org/abs/2504.15466).

- Kimi K2.5 Agent Swarm (Kimi Team, 2026). A trainable orchestrator creates up to 100 subagents and is trained with parallel-agent RL. Two ideas transfer directly. "Critical steps" charge each parallel stage at its longest branch, which gives a latency-aware cost for the Pareto result. "Serial collapse" names the failure where an orchestrator with parallel capacity falls back to sequential work; watch for it in prompt-only runs and treat it as a training target. Its orchestrator is privileged, and its subagents do not inherit state. (Abstract and secondary write-ups; check the reward details in the report.) [Report](https://arxiv.org/abs/2602.02276).

- WideSeek-R1 — Exploring Width Scaling for Broad Information Seeking via Multi-Agent Reinforcement Learning (2026). A lead agent and parallel subagents trained with multi-agent RL. Before training, results first improved and then declined as subagents were added, because the lead struggled with conflicting and redundant information. Evidence about where an untrained swarm's integration breaks, and consistent with prompting failure not gating training. [Paper](https://arxiv.org/abs/2602.04634).

- Hogwild! Inference (Rodionov et al., 2025). Several instances of one model generate concurrently over a shared KV cache, see each other's progress, and coordinate without training. A prompt-only reference for copies of the same model collaborating. [Paper](https://arxiv.org/abs/2504.06261).

- Collaborative Parallel Thinking — Share More, Search Less (Wang et al., EMNLP 2026). Parallel branches pool their discoveries at synchronization points instead of rediscovering them independently. Without training, this improves the accuracy-latency frontier on math tasks. Evidence for the value of the "what and when to communicate" decision in §0.1. [Paper](https://arxiv.org/abs/2605.27030).

- Second Thought — Reasoning in Parallel as LLM Agents Act and Observe (Sun et al., 2026). Forks auxiliary reasoning branches while the agent waits on a tool result and merges them when the observation arrives. Without training, it reports fewer turns and less main-thread decoding. Tool-wait time is idle model time that copies can fill. That is a latency lever separate from best-of-N, relevant to reaching the same latency at a lower $/token. (Abstract only.) [Paper](https://arxiv.org/abs/2608.13667).

- Don't Build Multi-Agents (Yan, Cognition, 2025). The strongest practitioner argument against parallel subagents: delegation briefs lose context, and parallel workers make conflicting implicit decisions. It states the problem behind §0.1's copy-versus-delegate distinction. A fork that inherits the full trace satisfies its context-sharing principle, and the conflicting-decisions concern becomes a communication and integration behavior the swarm can learn. [Post](https://cognition.com/blog/dont-build-multi-agents).

- How we built our multi-agent research system (Hadfield et al., Anthropic, 2025). On BrowseComp, token usage alone explained 80% of performance variance, and the multi-agent system used about 15× the tokens of chat. Evidence that parallel workers turn additional tokens into results on breadth-heavy tasks, with a concrete cost multiplier. [Post](https://www.anthropic.com/engineering/multi-agent-research-system).

- Towards a Science of Scaling Agent Systems (Kim et al., 2025). Controlled comparisons of agent architectures. Coordination helped on decomposable tasks and hurt on sequential planning, and returns diminished once a single agent was already strong. Relevant to the competence of staying serial when branching does not pay. [Paper](https://arxiv.org/abs/2512.08296).

16.3 Step 3 — evidence, selection, models, tasks, and budgets

- Scaling Test-Time Compute for Agentic Coding (Kim et al., 2026). Converts each rollout into a compact structured summary, compares summaries by recursive tournament voting, and conditions new rollouts on distilled summaries. It reports Claude 4.5 Opus rising from 70.9% to 77.6% on SWE-bench Verified and from 46.9% to 59.1% on Terminal-Bench 2.0. Its summaries are close to Weft's emissions and peer-facing labels (§4.2). Comparing summaries is a behavior the swarm can use when reading every trace is too costly. (Abstract only.) [Paper](https://arxiv.org/abs/2604.16529).

- SWE-Replay (Ding and Zhang, 2026). Branches from intermediate states of archived trajectories, restoring repository state from stored diffs, with a heuristic choosing branch points. It reports up to 17.4% lower cost on SWE-bench with resolve rates equal or higher. §6 keeps ended branches readable, so forking from an earlier point of a finished branch is an available swarm action. This is evidence that the action pays. [Paper](https://arxiv.org/abs/2601.22129).

- Evaluating Test-Time Scaling of General LLM Agents (Li, Xiong, et al., 2026). Across search, coding, reasoning, and tool-use tasks, neither sequential nor parallel scaling reliably helped; the authors attribute the parallel shortfall to a verification gap. For general use without a golden checker, the swarm's own evidence gathering is the binding constraint. Also a candidate source of tasks for §10.2 transfer. [Paper](https://arxiv.org/abs/2602.18998).

- The Limits of Inference Scaling Through Resampling (Stroebl, Kapoor, and Narayanan, 2024; first titled "Inference Scaling fLaws"). With imperfect verifiers such as incomplete unit tests, false positives cap what resampling can achieve. A reference for measuring swarm-generated evidence against withheld outcomes. [Paper](https://arxiv.org/abs/2411.17501).

- S* — Test Time Scaling for Code Generation (Li et al., 2025). Combines parallel and sequential scaling, then generates inputs that distinguish candidates and selects by running the candidates on them. A concrete discriminating-test behavior the swarm can adopt. [Paper](https://arxiv.org/abs/2502.14382).

- Risa — Disagree to Explore, Agree to Commit (Chen et al., 2026). Selects among parallel software-agent attempts by agreement in mixture-of-experts routing traces, without running tests. Evidence that model-internal signals can rank candidates where no checker exists. It applies only to open-weight MoE models, which fits local serving. (Abstract only.) [Paper](https://arxiv.org/abs/2608.22191).

- AI Agents That Matter (Kapoor et al., 2024). Makes the case for cost-controlled agent evaluation, with accuracy plotted against dollar cost as a Pareto frontier, and documents reproducibility and holdout problems in agent benchmarks. Methodology for the main dollar-cost Pareto result. [Paper](https://arxiv.org/abs/2407.01502).

Serving economics for the $/token operating point in §0.1 and §8:

- SGLang (Zheng et al., 2023). A frontend `fork` primitive plus RadixAttention, which keeps KV cache for shared prefixes in a radix tree. This is the serving-side mechanism behind the KV reuse from branching: every child's fork-time prefix is already cached. [Paper](https://arxiv.org/abs/2312.07104).

- DeFT — Decoding with Flash Tree-Attention (Yao et al., ICLR 2025). An attention kernel for tree-structured decoding that avoids rereading shared-prefix KV and balances tree-shaped KV across partitions, with up to 2.2× end-to-end speedup. Relevant when a local server decodes many branches of one loom together. [Paper](https://arxiv.org/abs/2404.00242).

- Autellix (Luo et al., 2025). Schedules an agent's LLM calls as one program using program-level statistics. It reports 4–15× higher program throughput than vLLM and SGLang at the same latency. The scheduling counterpart of the §0.1 hypothesis: run a loom's calls at an efficient batching point while holding task latency. [Paper](https://arxiv.org/abs/2502.13965).

- Unlocking parallel test-time scaling for long-horizon agents (Bhat, Doubleword, 2026). Ran 64 concurrent mini-swe-agent instances on DeepSeek-V4-Pro against all 731 public SWE-bench Pro problems on one 8×B300 node: 46,784 attempts in 24 hours, at about $0.05 each. A single attempt averaged 51.2%. Accepting any of the 64 reached 70.7%, which is an oracle bound rather than a selected result. A measured dollars-per-attempt reference for a throughput-oriented serving point. (Page partly truncated when read.) [Post](https://blog.doubleword.ai/swe-bench-pro-64-deepseek-agents).

16.4 Step 4 — prompt learning and behaviors the swarm can discover

- ATLAS — Agentic Test-time Learning-to-Allocate Scaling (Qin, Cao, and Xie, 2026). A prompted orchestrator decides when to dispatch another solver, when to stop, and how to synthesize. On HLE, LiveCodeBench, and GPQA it uses fewer calls than fixed workflows. Evidence that current models can make allocation and stopping decisions from a prompt. Its solvers start fresh, so it tests allocation without inherited state. (Abstract only.) [Paper](https://arxiv.org/abs/2606.01667).

- AB-MCTS — Wider or Deeper? Scaling LLM Inference-Time Compute with Adaptive Branching Tree Search (Inoue et al., Sakana AI, 2025). Adaptively chooses between generating a new attempt and refining an existing one. Weft faces the same choice as forking versus continuing. Read it as part of the behavior repertoire, not as a controller to adopt. [Paper](https://arxiv.org/abs/2503.04412).

- ACE — Agentic Context Engineering (Zhang et al., 2025). Evolves an agent's instructions as a playbook through incremental, curated updates. This avoids the collapse that comes from repeatedly rewriting a prompt wholesale. Complements GEPA for evolving the swarm's organization instructions across many runs. [Paper](https://arxiv.org/abs/2510.04618).

- Darwin Gödel Machine (Zhang et al., 2025). Open-ended, archive-based evolution of a coding agent's own harness, evaluated on SWE-bench and Polyglot. A reference for population and archive management in harness search, and for the evidence a later self-improvement claim (§10) would need. [Paper](https://arxiv.org/abs/2505.22954).

16.5 Step 5 — learning from traces

- TraceGraph (Nian et al., 2026). Builds a graph over action-observation states from pooled rollouts, marks "trap" regions, and evaluates continuations from the same prefix. A method for reading the loom record across tasks: where forks paid off, where branches shared a mistaken assumption, and which decisions to select for training. (Abstract only.) [Paper](https://arxiv.org/abs/2605.31308).

- MAST — Why Do Multi-Agent LLM Systems Fail? (Cemri et al., 2025). A taxonomy of multi-agent failures covering specification, inter-agent misalignment, and verification. A starting vocabulary for the §8 failure diagnoses and for labeling failed looms. [Paper](https://arxiv.org/abs/2503.13657).

16.6 Step 6 — VM state and later versions

- Morph Cloud Infinibranch. A commercial VM snapshot, branch, and restore service for agent workloads, quoted at under 250 ms per operation. A rental reference for live-process branching if the local VM path stalls. [Developer page](https://cloud.morph.so/developers).

- forkd (jrimmer). A KVM microVM fork tool. It claims 100 children in about 100 ms from a warm parent and live-VM branching in about 150 ms. Add it to the step 6 candidates and test it against the §11 conformance recipe. (README only.) [Repository](https://github.com/jrimmer/forkd).
