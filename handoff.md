# Weft — Forking the computer

Project handoff

## Part I — Introduction: copies are the native affordance

Humans have a single continuing existence and cannot trivially copy themselves into simultaneous continuations. That pattern casts a shadow over how we design agents. A digital agent, by contrast, can copy their working state and pursue several continuations at once. The resulting tree of existences is beyond human comprehension, much like the models themselves. But much existing work forebodes much better performance and lower cost. Best-of-N evaluations show increased performance, and fork-summarize-and-join models decrease cost, but these systems are overly constrained by a desire for control and full understanding. No work has delivered a fully transparent, continuously and recursively trainable loom for arbitrary graphs of machine states. This project takes the bitter lesson instead: learn the organization of the tree rather than prescribe it.

The key primitive this project uses is a fork of the full machine+agent state, the session and the executable workspace branch together, available to the models as a tool call. Instead of the prescribed parallelism used today, we build a loom that includes the state of the computer itself. A copy can act on the files, artifacts, and tool results accumulated so far without reconstructing the situation from a description. Taking the bitter lesson seriously means learning the organization policy from outcomes. Because there are no other new primitives, the swarm determines when to fork, where, to which model or specialization, how wide, how much context to inherit, what each branch should do, what and when to communicate, what evidence to use, which results to incorporate, and when to stop without any external managing infrastructure. The swarm owns selection, integration, and final delivery, and chooses whether to interrupt a peer or consult a quarantined copy of the peer (§5). Since these decisions are models', the paradigm grows more capable and efficient as the models do and is recursively trainable.

Relative to training agents to generate and run massively parallel tasks themselves, forking lowers the burden of asking for help. Invoking a specialized subagent or predefined workflow ordinarily asks the agent to recognize both that they need help and what kind of help to request. A fork requires only the judgement that another continuation could be useful. The copy inherits the situation and can discover what work is needed without interrupting the original thread. A detailed task decomposition or specialist brief is optional. This also preserves information whose importance the parent has not yet recognized and therefore might omit from a delegation brief.

The same lowered burden reaches the user, a being more limited, but still part of the larger implicit loom that extends beyond the explicit computer. Just as a session cannot always know what help they need, a user cannot fully plan before anything has been built, and models do not have perfect judgement about which gaps matter. The current compromise is to follow the specification closely and ask sparingly about ambiguities, and each question costs a turn. With a fork, an ambiguity or a discovered improvement gets its own branch: the original specification is delivered, and a candidate that may be better is delivered alongside it, from the same state, so the user picks rather than answers. When to open such a branch and whether to deliver it are trainable like the rest.

Delivery and improvement separate the same way. Today a session returns the result as soon as it meets the specification. They are trained to deliver any usable result at low cost. With a fork, the live session can return at the specification while copies keep working on performance, without touching the base project or session (§2). Higher performance is delivered without cluttering the context or machine state with speculative changes or decreasing user interactivity. Mistakes even in the main session are cheaper for the same reason. Every fork is a snapshot of the session and the workspace, snapshots stay readable after their branch ends (§5), and a fork can target an earlier one (§4), so when an agent oversteps or a merged change proves wrong, rollback is a fork from the state before it rather than a repair. The cost of a wrong decision falls to the cost of noticing it.

One of the key use cases of this ability to speculate is to test whether something generated outside the current context is useful without committing to it. This is the insight behind our only meta-primitive, a small wrapper around fork: consult (§5). A quarantined copy of a target session runs an interruption so the live session does not have to. Consult can be used for resolving forked sessions by effectively messaging the parent session without polluting their context unnecessarily. It can also be used in an open-ended scheduled search: a copy looks for potentially useful information, in memory, in the transcript, or outside, tries to apply it in context, and forwards it to the live session only when it helps. Memory becomes an ordinary use of the fork rather than a system of its own.

Even though the system described here would be a significant change in the way we use agents, the economic case rests on established results. The rise of Mixture of Experts (MoE) models has shown that frontier capabilities do not depend on all the weights operating continuously and with dense connection. The success of subagents and summaries has shown that the average context can stay small without hurting performance. Managed best-of-N has shown higher performance at lower cost and that parallel work shortens a task's latency while maintaining its performance. Lower task latency allows running inference servers at more profitable operating points without hurting end users' project timelines. These are all examples of exploiting the tree of machine states for higher performance and lower cost, but they do not make that tree trainable or transparent.

Since the techniques are not transparent to the user, deployed agents do not make full use of them, so their realized economic value is limited. Each is a prescription: someone decides in advance when to branch, what to delegate, and how to combine the results. Improving a prescription takes specialized training; gains in the base model's general intelligence only reach it partially. Almost any task can benefit from forking, and deciding to fork only requires a judgement on uncertainty, so it is generic across tasks. Generic means trainable without special treatment.

And the trainability extends to follow-up architectures likely to increase model performance beyond the frontier. The same primitive extends from identical copies to transparent model specialization (§12.1): one base model controls the root session while forks can target models differentiated by prompting or weights. This allows capturing the benefit of specialization demonstrated by MoE. Token-level MoE routes every token across experts and requires tight, high-bandwidth interconnects; routing at `fork` shifts communication to branch boundaries and compact emissions, so specialized models on separate modest machines can do substantial local work over the inherited session and workspace before reporting back, without prescribed specialist roles or lossy delegation briefs.

The loom also feeds its own training, transparently. Every branch ends with an outcome and a cost, an implicit label; more idle compute raises the budget, more budget means more branching, and more branching means more labeled data, with nothing polluting the user-visible session. Training is not a separate process either, and not a new primitive: a session that judges training useful forks into it, and the copy trains themselves or a companion model while the live session continues, so the benefit arrives without the cost to the task and nothing is hidden (§12.3). Which specialist to grow, on what, and how is decided the same way and rewarded the same way, when the loom improves. The domains with no hand-trained specialist, a new programming language, a poorly documented field with a small market, hardware design, gain access to frontier-level intelligence with the only constraint being available compute.

The bitter lesson bears on hardware as well. The most capable models are being built to target hardware that is extremely expensive and not widely available: large nodes with tight interconnects. If scaling is the priority, the target cannot be one machine scaled up indefinitely. It has to be models small enough to run on devices that are distributed geographically and in every other way devices can be distributed, which means consumer-level hardware in very large swarms. The same argument was made in systems research when large shared-memory multiprocessors were the frontier: on economics alone, clusters of commodity machines won, and high-performance computing then built its supercomputers from commodity parts (§14.6). Note that none of this implies that the collapse in the cost of programming leaves consumer hardware untouched: the shape of that compute is likely to change now that humans are not the ones programming it (§13).
